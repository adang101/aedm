# Design

AEDM ("Autonomous Enhanced Dungeon Master") is a browser game where an LLM runs the table for 2 to 6 players. Players host or join a lobby with an invite code, build characters, and play a campaign the DM generates and adapts as they go. The rules engine owns every number; the model proposes and the engine decides.

The other docs (`contracts.md`, `rules-numbers.md`, `spike-kit.md`, `style-bible.md`) are guides, followed loosely. Where the code deliberately diverges, this file says so.

## Architecture

```
apps/web  ──WebSocket (contracts.md messages)──▶  apps/server
 Canvas 2D renderer, lobby UI, chat, sheet         rooms, lobby, turn loop, persistence
                                                     │
                                  ┌──────────────────┼──────────────────┐
                                  ▼                  ▼                  ▼
                           packages/engine     packages/llm      packages/schemas
                           pure rules, RNG,    ModelProvider,     Zod contracts shared
                           mapgen, validators  prompts, DM/forge   by every package
                                               orchestration
```

| Package | Responsibility | May do I/O |
| --- | --- | --- |
| `packages/schemas` | Zod schemas for every contract; inferred TS types | No |
| `packages/engine` | Seeded RNG, dice, checks, attacks, combat, conditions, ability cost, threat, point buy, map generation and validation, DM action validation and application. Rules numbers in `data/*.json`. | No (no `Date`, no `Math.random`) |
| `packages/llm` | `ModelProvider` interface, Anthropic provider, fake provider, prompt files, context builder, DM turn / ability forge / enemy builder pipelines (parse, one repair, engine validation) | Network, via the provider only |
| `apps/server` | Node + `ws`. Lobbies, invite codes, presence, intent batching, turn loop, broadcasting, JSON saves | Yes |
| `apps/web` | Vite + TypeScript. Lobby, character creator, map view, chat log, combat HUD | Browser |

## Game loop

**Exploration.** Players move freely on the map (`move_intent`, validated by the engine against the `walls` layer) and speak in character (`say` with channel `ic`). The server batches in-character intents into a *beat*: the beat closes when every present player has acted or after a short window. The batch, plus a context pack (digest, facts, scene, party, recent turns), goes to the DM. The DM's JSON response is parsed with Zod, repaired at most once, then each action is validated and applied by the engine in order. Rejected actions are dropped and logged. Narration streams to clients.

**Checks.** `request_check` pauses the beat: the engine rolls (with tag bonus, advantage), broadcasts `roll_result`, and the result is fed back to the DM as an `[engine:]` line for the follow-up narration.

**Interaction (what the engine resolves and what goes to the DM).** The `act` message and the typed commands above go through `performAct`: doors, levers, signs, chests, piles, remains, locks (key, pick, force), `examine`, and item moves (`container_action`, `inventory_action`) are engine calls with no model call. Engine lines reach the DM only as `[engine: ...]` context on its next call; deterministic text (an examine line, a sign) is broadcast to the table as a log line. Searching (`act` `search`, no target), disarming a revealed trap and taking an altar's boon are engine calls too (decision 26). Only what the engine cannot describe reaches the DM as an intent: `talk`, a creature, `interact` on one, and any typed text the router does not recognize. In combat the same verbs run through the combat action path (own turn only, cost from `interact.json` `combatCost`). Looking around, checking the pack, waiting, using a carried healing draught, and examining a creature are engine lines too (decision 22). The DM shapes these systems with three actions, `stock_container`, `set_sign_text` and `set_lock` (decision 18), and sees containers and objects in `<scene>`.
**Combat.** `start_combat` hands control to the engine: initiative, turn order, a turn timer, movement within speed, basic attacks, abilities and items. Enemies act through their behavior tags with simple heuristics. Ordinary rounds are narrated by the engine's deterministic narrator (no model call). In the default lean mode (`ServerConfig.combatDm: "lean"`, decision 19) the engine also starts fights itself (the attack button, a typed attack, creatures noticing the party; decision 20), writes the opening, short barks when a creature's nerve breaks and the close of an ordinary victory, and the DM is called only for a party member going down, a boss or elite falling, player speech, a defeat, and a victory that involved a boss or elite or left a hero down. In `"full"` mode the DM is called at combat start, for every reaction event (morale, surrender, flight, bloodied, a PC dropping to 0 HP, a boss or elite going down) and at combat end. Either way the DM may start a fight with `start_combat` and end it with `end_combat`.

**Intent routing.** Before a beat reaches the DM, `classifyIntent` (engine, pure) sorts each intent into `mechanical` (empty input, `/ooc`, a compass step, a walk to a uniquely named door, chest, exit or non-hostile character, the typed object commands, looking around, checking the pack, waiting, using a carried healing draught, examining a uniquely named creature, and attacking a uniquely named enemy) or `narrative` (everything else, including every command with an extra clause). The server resolves mechanical intents with engine calls; a typed attack starts an engine fight in lean mode and still goes to the DM in full mode (decision 20). If every intent is mechanical there is no DM call and the engine lines wait for the next one; otherwise the beat goes to the DM as before, with the mechanical results passed as engine lines. Free text is never blocked.

**Enemy tactics and morale.** The engine reads an enemy archetype's `behavior` text with case-insensitive patterns from `rules.ai.tactics`, compiled once, exactly like the ranged-attacker pattern: `focus_weakest`, `target_healer`, `protect_leader`, `pack`, `fearless` and `cowardly` (fearless wins over cowardly, so "never retreats" is fearless). One ranking function orders foes for both abilities and basic attacks; with no tactic it is the old order (nearest, lowest HP, id), and a taunt still comes first. Allied NPCs and autopilot PCs have no archetype and no tactics. Morale (`rules.ai.morale`): at the start of its turn, an enemy below its role's threshold (minion 50%, standard 30%, elite 20%, boss never; cowardly adds 20) rolls a d20 once per fight against DC 10, and failing breaks it. Minions break at once when the last boss or elite on their side falls. A broken enemy never attacks: it runs to the reachable tile farthest from its foes. When every foe is 8 or more tiles away, or it stands on a map edge or an exit, it flees and leaves the map and the turn order. If it cannot get any farther away it surrenders instead: it becomes a wary NPC (role bystander, with a dossier record) outside the turn order, so the party cannot attack it and the DM can talk through it with `npc_say`. A fight whose remaining enemies fled or surrendered is a victory. The engine events `morale_broken`, `fled`, `surrendered` and `bloodied` (a boss or elite first dropping below 50% HP) are logged for players and sent to the DM, which reacts before the next turn (decision 9). Further AI rules (`rules.ai`, decision 23): an area ability is aimed at the tile that catches the most foes and fewer allies than foes, a creature with a heal or shield ability uses it on a hurt ally, a ranged creature with a foe next to it steps away to a tile with range and line of sight (kiting), a foe it can plausibly drop this turn is targeted first (finishing blow), and fire and visible traps of the other side are walked around when a short detour exists. Out of combat, hostile creatures that see a party character within 8 tiles start the fight (aggro), and allied NPCs follow the party (decision 24). Allied NPCs created with role `ally` carry a combat stat block (the standard enemy for the party level, HP and damage scaled by `npc.allyStatPct`, 75) and fight on the party's side through the same AI turn as enemies, without archetype tactics or morale.

**Never game over.** A total party wipe becomes a consequence narrated by the DM.

## AI layer

- Every call goes through `ModelProvider` with a tier: `fast`, `standard`, `strong`. `high_stakes` routes the next DM call to `strong`.
- The Anthropic provider maps tiers to configurable model IDs (defaults: Haiku, Sonnet, Opus of the current family).
- The fake provider returns scripted, schema-valid responses. Tests and offline play use it; no test calls a real model.
- Prompts live in `packages/llm/prompts/*.md`.
- Not every moment needs a model. Routine, mechanically determined moments are handled in the engine: combat round narration (`packages/engine/src/narrate.ts`, phrasings in `data/narration.json`, picked with a seeded rng and filled only with names and numbers from the events) and mechanical intents (`packages/engine/src/intents.ts`). Also without a model: scene, creature and pack descriptions (`describe.ts`, `data/describe.json`), a fight's opening, creature barks and the close of an ordinary victory (`combat-voice.ts`, `data/combat-voice.json`), the choice of who fights and at what difficulty when the engine starts a fight (`engage.ts`), enemy stat blocks (`enemy-builder.ts`, `data/enemy-kits.json`, the default `enemyBuilder: "engine"`), and out-of-combat aggro and ally following (`npc-behavior.ts`). The DM still sees everything: engine lines accumulate for its next call, and a round with more than `digestAtLines` lines is collapsed into one digest line. Player free text typed during combat is kept in recent turns and reaches the next DM call.
- **What the DM sees each turn (token budget).** The system prompt (rules plus action catalog, with the sorted material id list) is fully static so provider prefix caches hit. The user message is not cached and is kept small:
  - Empty sections are omitted (no "(none)" blocks). Tags the system prompt names: `<campaign>`, `<summaries>`, `<canonical_facts>`, `<scene>`, `<party>`, `<quests>`, `<milestones>`, `<pacing>`, `<recent_turns>`, `<engine_results>`, `<cast>`, `<limits>`, `<player_input>`. The only prose kept is a one-line untrusted-input notice before `<player_input>`.
  - Facts: at most 20 and about 2,400 characters (`CONTEXT_LIMITS`). Facts about something in the scene, the party or the current map, and all `is_alive` facts, come first, then the newest; output stays chronological with a "N other facts not shown" line.
  - Party lines carry id, name, title, level, hp, tags and ability names only when present, items, and `(away)` for absent players. No player names.
  - Entities read `id "name" kind @x,y`, with hp only when wounded and no coordinates for objects.
  - Milestones: open ones of the current and next stage, plus a count of completed and of later ones. Quests: active ones in full, closed ones as one line of titles.
  - Recent turns: player lines verbatim (escaped, untrusted); DM turns except the latest are cut to 40 words. The window stays at 12 turns.
  - Pacing is two lines.
  - Compact refinement lines (caps in `CONTEXT_LIMITS`): `<npcs>` is one line per NPC, `- npc_1 "Name" role disposition @here|map_id [hp x/y]: concept | voice: ... | said: "..." | notes: ...`. NPCs on the current map keep the concept (140 chars), voice, the last 2 lines said and the last 3 notes; NPCs elsewhere keep only role, disposition, map and their last 2 notes; the dead are `- npc_2 "Name" dead`. `<combat>` is one line per creature in the same style as `<scene>`, `- ei_1 "Cantor" enemy hp 9/40 [dazzled] boss broken bloodied: concept | does: behavior` (two behaviors at most). `<dm_notebook>` keeps the newest 4 notes of at most 45 words each, `<threads>` the newest 8 (120 chars each), `<summaries>` the newest 3 chapters of at most 60 words each. All model-written text stays escaped.
  - A repair call for a DM reply sends only the system prompt, the bad reply and the errors (`repairContext: "minimal"`), never the full context. Other repairs (forge, enemy, bible) still resend their small requests because their checks are semantic.
  - Output caps per purpose live in `MAX_OUTPUT_TOKENS` (`packages/llm/src/provider.ts`), sized to the largest valid reply plus room for hidden thinking tokens.
- Ability forge: the forge adapts a player's idea to the story and the engine rather than transcribing it. Besides the concept and ability text it sees the campaign (the story bible's title, digest and tone in a game; the room's pitch in the lobby), the other characters' abilities as one-line summaries plus the character's own earlier ones (so sets stay varied and teammates are not duplicated), the character's power budget with a per-ability target, and a short cost guide the engine renders from `costs.json`. It may rename and reflavor an ability but keeps the core effect, and always explains what it changed in `forge_notes`. At creation each ability is forged against `floor(remaining budget / abilities left)`; the engine clamp and the repair call shape it to fit, so abilities are no longer dropped for cost (dropping the last ones stays only as a safety net). Level-up forges against the budget that is left.

**Memory and continuity.** The DM keeps a story straight from what each turn's context hands back, never from the model's own memory.

- *Notebook:* the DM's private `dm_notes` come back as `<dm_notebook>` (the last 8 are stored, `ServerConfig.dmNotebookLimit`; the newest 4 are rendered, trimmed to 45 words). They are model output, so angle brackets are escaped.
- *NPC dossier:* each NPC record keeps its `voice`, the last 3 lines it said and the last 5 DM notes (`npc_note`), plus the beat it was last seen. `<npcs>` lists up to 12 NPCs, not only those on the current map: the ones here first, then the most recently seen, with the dead last as one short line each so they are never brought back. `<scene>` still lists the entities on the current map for ids and positions.
- *Story threads:* `open_thread` and `close_thread` keep a short list of unresolved clues, promises, debts and dangers in the game state; `<threads>` shows the open ones (at most 12).
- *Current act:* `currentAct` (engine, `plot.ts`) maps the current stage onto the bible's acts proportionally (`floor(stageIndex * acts / stages)`, the last act once the story is finished). Without a plot the milestone progress stands in for the stage. It appears in `<pacing>`, or in `<campaign>` when there is no plot.
- *Tiered summaries:* a chapter (at most 120 words, only its own batch of 20 turns) is written when the recent turns pass 36; the last 4 chapters are kept, and a fifth folds the oldest into `story so far` (at most 250 words). Both calls use the `fast` tier (`summary.md`, `story-so-far.md`). If a call fails, the turns return to the recent list and nothing is lost; a failed fold keeps the extra chapter for the next try.
- Prompt changes (`dm-system.md`, `summary.md`, new `story-so-far.md`): the evals were not run. The token-diet pass that compressed `dm-system.md` (system 5,289 to 4,922 tokens) and the refinement context lines (typical call 7,839 to 7,324) also changed prompt text and context formats: `pnpm eval` must be run before a release.
- The DM response `v` stays 1: the change adds optional fields and action types. Saves keep loading (see `contracts.md`).

## Content model (maps and sprites)

The DM can ask for any place or creature the story needs. It never draws tiles or pixels; it writes a structured *spec*, and deterministic engine code turns the spec into a valid, renderable component. The same spec later feeds the image model, so procedural placeholders and generated art share one contract.

**Maps: setting + layout + materials.**

- A map brief names an open-ended `setting` (any name: "sunken cathedral", "airship deck", "glacier rift") instead of choosing from five biomes. The setting picks one of a fixed set of **layout generators** (rooms and corridors, cave, open field, settlement, trail, arena, maze, islands), an environment (indoor, outdoor, underground), a mood, and a set of **materials** for each role: floor, path, wall, obstacle, liquid, hazard, decor props.
- **Materials** come from a data library in `packages/engine/data/materials.json` (each has a role, two colors from the palette, a pattern, walkability, sight blocking, tags and a `prompt_traits` line for the image model). The DM may also define a new material inline; the engine validates it, snaps its colors to the master palette and picks a pattern from the allowed list. A name the library does not know resolves by id, then tag, then role, so an unusual request never fails.
- Each generated map carries **its own inline tileset** built from the resolved materials, so the client can draw any map with no fixed catalog. The five old biomes become **setting presets** in data.
- Legibility rules (engine, tested): every resolved setting keeps a minimum luminance contrast between its wall and floor or path colors (`MIN_WALL_CONTRAST`), mood words in the setting name or tags (sunken, haunted, cursed, drowned) push the mood toward eerie, indoor maps use at most two floor materials, and secondary path materials form whole stretches rather than single tiles. `?mock=1&gallery=maps` renders every preset, layout and several free-text settings for visual QA.
- Reliability: the brief is schema-checked, materials resolve to a known role, the layout generator runs with a seed, and the map must pass the validation rules (3 seeds, then simplified rooms, then the preset's own layout, then a single plain chamber; it throws only if all of that fails).

- Interactables are mechanics, not just markers: a chest can be locked and holds items, a door blocks movement and sight while closed or locked, a lever opens the doors it is linked to, a sign carries text. The map object records how it was built; the game state records what it is now (`GameState.containers` and `interactables`), so a map stays shared and unmutated and every snapshot merges the two. `buildMap` fills in locks (DC by tier), sign text and lever links from data with its own seeded stream, so layouts do not change; chests and loot slots become containers with seeded contents when the map is added. See `contracts.md`, "Containers, locks and doors".

**Sprites: body plan + parts + palette.**

- Every NPC, enemy, character and prop uses one `SpriteSpec`: a **body plan** (humanoid, beast, avian, serpent, insectoid, amorphous, construct, spirit, plant, object), a **size** (tiny to huge), a **palette** (primary, secondary, accent, detail colors snapped to the master palette), up to 6 **parts** from a catalog (horns, wings, tail, hood, robe, armor, shield, weapon kinds, crown, mask, glowing eyes, tentacles, spikes, aura, and so on), and a `traits` line for the image model.
- A **sprite designer** step turns a concept ("a robed chorister who borrows the voices of the drowned") into a spec: a fast-tier model call through `ModelProvider`, validated by schema, with a deterministic keyword designer as the offline fallback. The web client composes the spec procedurally on the 48 x 64 canvas.
- **Asset store:** specs (settings, materials, sprites) are cached by a hash of their concept, so recurring places and creatures reuse their look across a campaign. An `image_asset_id` slot on each spec is where generated art will plug in (M3).

**Natural terrain (engine).** Generated maps are built from smooth seeded fields (elevation, moisture, grove, wander), made with value noise in the engine and never the map RNG, so a map stays a pure function of brief and seed. The fields drive: ground material zones (damp ground takes the second floor material and groves the third, with minimum patch sizes so no isolated specks remain); lakes that grow from low ground, and sometimes a winding river; least-cost paths over a noise-perturbed cost field that link rooms, exits and landmarks, bridge open water, ford shallows and widen at junctions; clustered groves and outcrops with clearings around the arrival area, combat rooms and focal rooms; and a treeline of variable depth instead of a picket row. Open fields, trails, islands, caves and settlements use these; rooms and corridors, arena and maze only get the ground zones. All numbers live in `packages/engine/data/terrain.json`. Obstacle tiles carry a species code the assembler maps onto the setting's materials. Known weak spots: settlements (a clashing secondary plaza material, patchy roofs, stepped canals), plain swamp, desert and snowfield maps, and rivers that can come out wide.

**Terrain rendering (web).** The client draws the static ground of a map from a per-pixel material grid, not from per-tile stamps. Ground materials layer by role (liquid, floor, path, hazard; deep water over shallow, ties broken by a stable hash). A higher material reaches into the lower cell by a wobbling distance derived from noise at the world pixel, so material boundaries are organic pixel edges and every client draws them the same. Water gets a foam line, a shallows band and a darker centre by distance to the shore, plus a few animated glints. Large fields get low-frequency tone variation and hashed scattered details chosen from role, pattern and the words in the material id. Walls cast a two-band shadow to the south and east and a cave setting rounds the rock edge. All static terrain is pre-rendered into cached 8 x 8 tile chunks (built when first near the view and ahead of the camera in small time slices); each frame blits the visible chunks and draws only water glints and hazard motifs. All variation is a function of map id, world position and material, never of draw time. The gallery's "Material transitions" section shows pairs of ground materials on a small synthetic map.

**Map overview (web).** The client shows a minimap, a location title card and point-of-interest labels, all computed from the map the client received. The minimap reduces each tile to one readable class (ground, path, water, hazard, wall, obstacle, door) tinted by the tile's own colour, pre-rendered at one pixel per tile and repainted only when the camera view, a creature or the visited area changes. It marks exits on their edge and visible interactables and loot piles with glyphs, shows creatures by shape (you, party, friendly, neutral, wary, hostile) and frames the camera. Hidden traps and chests are never shown: only objects the server sent appear. Unvisited ground is dimmed from where the party has stood this session (a client-side convenience, not fog of war; the map itself always arrives whole). Click or drag looks there; a quick second tap walks there. The panel header carries the place name; collapse is remembered per browser, with a collapsed default on narrow screens, and a whole-map view is available. A title card names the place on arrival (first snapshot and every scene change), and the story log gets one named line per scene change; the engine's id-only arrival line is dropped by the client (the server should name the map itself; not done yet). Interactables and exits get labels near the party or under the pointer.

**DM scene objects.** The scene lists map objects nearest the party first (as it already did for containers), so the context cap never cuts what is beside the party.

## Player-made sprites (built: Describe, Paint over, Paint from scratch, Workshop and campaign cast)

Players can make the look of their own character, and of NPCs and enemies they offer to a campaign, in three ways. Every way ends in the same sprite recipe, so the renderer, the DM and the asset store treat all of them alike.

| Way | What the player does | Result |
| --- | --- | --- |
| Describe | Writes up to 300 characters ("a lanky heron-folk ferryman with a lantern and a patched blue coat") and picks a role | The sprite designer (the same pipeline the DM uses: fast-tier model, offline keyword fallback, engine finalizer) returns a `SpriteSpec`. The player can regenerate (a new seed), then fine-tune it in the parts builder. |
| Paint over | Opens any spec sprite in the pixel editor | The composed front idle frame is rasterized to a 48 x 64 grid and becomes editable. Saving keeps the original spec as `base` (for traits, fallbacks and the image model). |
| Paint from scratch | Opens a blank 48 x 64 canvas | A pixel sprite with no base spec. |

**Built (Describe path).** The creator's "Describe your look" box sends `design_sprite` (prompt up to 300 characters, `role_hint`, optional `seed` and `name`); the server answers `sprite_designed` (`spec`, `notes`, `source` of `model` or `offline`), correlated by the envelope id. Divergences from the plan: the result is never cached in the asset store (a re-roll must differ, so the designer runs fresh each time, with the usual 4 s timeout and offline fallback), and the offline look varies with the seed while a real model simply answers again. Calls are limited to 6 per minute per account (per connection for guests), set in `DEFAULT_CONFIG.limits.spriteDesign`. In the builder, an untouched design is kept whole (any size, up to six parts, traits and pose); touching a control builds on top of it with at most four parts. `?mock=1` answers with the offline designer. WS_VERSION is 5 (see the pixel sprite note below).

**Built (Paint over, Paint from scratch).** The creator's "Paint your own" row opens the pixel editor as a modal: "Paint over" rasterizes the current look (composed front idle frame at medium scale, feet on y = 60, colors snapped to the master palette) and "Paint from scratch" opens a blank canvas; "Edit painting" reopens a saved one. Saving puts the `pixel` recipe in the creator (preview, claim); changing the builder, designing again or randomizing replaces the painting, and "Remove painting" returns to the builder's spec. The editor's pure logic is `apps/web/src/state/pixel-editor.ts`; the DOM is `apps/web/src/ui/pixel-editor.ts`. Validation is live and Save stays disabled until it passes; feet off the guide by more than 4 rows are shifted automatically. Divergences: the editor keeps master palette ids and builds the recipe palette from the colors in use (so the 32-color limit is counted on distinct colors used), L and R select line and rectangle and a toggle picks filled or outline rectangles, recent colors are kept per editor session only, and the painted `size` is the builder's size at the time. The server validates on `claim_character` and answers `invalid_sprite`. The renderer draws `pixel` recipes without the spec outline pass (the painter owns the outline) and with no pose shaping.

**Pixel sprite.** A new recipe kind, `pixel`: 48 x 64 pixels, a palette of at most 32 colors drawn from the master palette plus the outline color, and pixels stored as palette indices (0 is transparent) in a run-length encoded string. Alpha is therefore only 0 or 255, as the style bible requires. Facing left mirrors the image; the idle bob, shadow, HP bar and rings are added by the renderer as for spec sprites. Large and huge sizes scale it with nearest-neighbor. The encoded sprite must fit in a client message (8 KB).

**Validation (engine, pure).** Exact size; every index inside the palette; every palette color on the master palette; at least 60 opaque pixels; no opaque pixel within 2 pixels of the canvas edge (style bible margins); feet within 4 pixels of y = 60 (auto-shifted if not). Failing sprites are rejected with the reason shown in the editor's "Check" panel before saving.

**Pixel editor (web).** Pencil, eraser, bucket fill, eyedropper, line and rectangle, a mirror-symmetry toggle (useful for front-facing chibis), undo and redo (50 steps), grid zoom from 4x to 12x, the master palette grouped by ramp with recent colors, an onion-skin of the base spec when painting over, and a live preview at 1x, on a floor tile and in both facings. Works with mouse, touch and pen. Keyboard shortcuts: B pencil, E eraser, G fill, I eyedropper, M mirror, Ctrl+Z and Ctrl+Y.

**Built (Workshop and campaign cast, WS v6).** Accounts get a Workshop (`<data>/accounts/workshop/<user>.json`, one file per account, atomic writes) with the limits below; contracts are in `contracts.md`. The web client has a Workshop modal (home account bar, lobby cast panel, creator): design a look for a pc, NPC, enemy or prop through `design_sprite` with a role picker, save, edit details, "Edit painting" in the pixel editor (a spec asset gets "Paint a copy"), and delete. The creator's "Save look to Workshop" keeps the current look, designed or painted. The lobby shows a cast panel: the host's `custom_cast` and `custom_paintings` settings, entries with Approve, Deny, Remove (host) and Withdraw (owner), an offer list from the viewer's Workshop, and per-viewer hide switches. Hide switches (one per entry, plus "hide all painted sprites") are stored in `localStorage` only and swap the sprite for a neutral shape in the renderer. Divergences: only `npc` and `enemy` looks can be offered (pc and prop assets stay in the Workshop), the cast is not saved with the campaign, the host and owner controls exist in the lobby only (the server accepts them in game), the host may change only the two cast settings once play has started, a cast entry is a snapshot (later Workshop edits do not change it), and `?mock=1` has a Workshop and cast too (`__mock.simulateOffer()` adds a pending offer from a fake player). Prompt change (`dm-system.md` now explains `asset_ref`): the evals were not run.

**Design notes (original plan).**

- Each account has a **Workshop**: a library of its own sprite assets, each with a name, role hint (pc, npc, enemy, prop), a short concept, the recipe and its source (designed, painted over, painted).
- A player can offer a Workshop asset to the current campaign's **cast**. Room setting `custom_cast`: off, host approval (default) or open.
- The DM's context lists the approved cast (name, role hint, concept) and may use an entry with `create_npc` or `create_enemy` by setting `asset_ref`. Looks and concept come from the player; the enemy builder and engine still decide every number, exactly as for DM-invented creatures.
- A character's own sprite can be any recipe kind, including a pixel sprite.

**Safety.** Painted images can contain anything, so: the host can turn custom paintings off for the room, anyone can hide a custom sprite for themselves, the host can remove one from the campaign, and painted sprites are only visible inside rooms the owner plays in. The automated image gates from the style bible (including the classifier) apply when the image pipeline lands (M3). Prompts follow the same rule as all text: no names of real people, other games or franchises; the finalizer strips them from traits.

**Limits.** 200 Workshop assets and 5 MB per account; sprite design calls are rate limited per account (they cost money once a real model is attached).

## Story structure

Every campaign follows one of seven classic **plot patterns** and one of six **emotional arcs**. The pattern decides *what kind* of story it is and its stages; the arc decides whether the party's fortunes trend up or down between them. Both guide pacing; player choices still win, and the DM re-aligns the plan rather than railroading.

**Plot patterns** (stages in order):

| Id | Shape | Stages |
| --- | --- | --- |
| `overcoming_the_monster` | A threat grows until the heroes confront and destroy it | call, early success, frustration, nightmare, final confrontation |
| `rags_to_riches` | The humble rise, lose everything, and earn it back for real | humble start, early rise, central crisis, independence, final union |
| `the_quest` | A long journey toward a goal through trials and temptations | call, journey, arrival and frustration, final ordeals, goal |
| `voyage_and_return` | Into a strange world, then a hard escape home, changed | fall into the strange, fascination, frustration, nightmare, escape and return |
| `comedy` | Confusion and misunderstandings pile up, then untangle | order disturbed, confusion, peak of muddle, revelation, reconciliation |
| `tragedy` | Ambition or a flaw leads to ruin (softened to loss at "family") | anticipation, dream, frustration, nightmare, downfall |
| `rebirth` | A dark spell or flaw holds sway until redemption breaks it | shadow falls, apparent calm, tightening grip, darkest hour, awakening |

**Emotional arcs** (fortune curve across the campaign; player-facing names are descriptive):

| Id | Shown as | Curve |
| --- | --- | --- |
| `rise` | Steady climb | up |
| `fall` | Long descent | down |
| `fall_rise` | Into the pit and out | down then up |
| `rise_fall` | Soaring, then falling | up then down |
| `rise_fall_rise` | Rise, fall, rise again | up, down, up |
| `fall_rise_fall` | Hope between two falls | down, up, down |

**Data.** `packages/engine/data/plots.json` holds, for each pattern, its stages (id, purpose, tension target 0 to 10, a suggested encounter difficulty, typical scene kinds and milestone templates), and for each arc a fortune curve sampled per stage. Recommended pairings are listed per pattern (for example `tragedy` with `rise_fall`), but any pairing is allowed.

**Flow.**

1. In the lobby the host picks a pattern and an arc, or leaves either on "Auto". Auto picks deterministically from the pitch keywords and the seed.
2. The story bible prompt receives the stage list and the fortune curve. The bible gains `plot: { pattern, arc, stages: [{ id, title, goal }] }` and every milestone carries a `stage` id. The engine validates that every stage has at least one milestone, in stage order.
3. During play the context pack adds a pacing block: current stage and its purpose, tension target, fortune trend ("this stretch should leave the party worse off"), and the suggested difficulty. The current stage is the stage of the first incomplete milestone; completing the last milestone of a stage advances it.
4. Suggested difficulty only sets the default for encounters; the engine's threat budgets still apply.
5. If the party abandons the planned path, the DM may re-plan the remaining stages with an `adjust_plot` action (new stage goals and milestones for stages not yet started; completed milestones never change).

**Built.** `plots.json` holds each stage's id, name, purpose, tension target and suggested difficulty, each arc's fortune per stage, and per pattern keywords and recommended arcs; scene kinds and milestone templates are not in the data yet. Engine: `pickPlot`, `plotOutline`, `validateBiblePlot`, `currentStage`, `pacingBlock`, and `adjust_plot` and stage-order checks in `applyDmActions`. The server resolves the room settings before bible generation and the bible prompt receives a `<plot_plan>`. Divergences from the plan above: the lobby option is called "Auto" (setting value `auto`); the engine also rejects `complete_milestone` for a stage later than the current one, so stages complete in order.

**Evals.** `packages/evals` (`pnpm eval`) holds the spike kit's E01 to E20, memory and continuity scenarios E21 to E26 (notebook payoff, NPC dossier promise, dead NPC in the dossier, thread payoff, thread cap, stage order), combat-presence scenarios E27 to E30 (parley, taunting boss, stunt, truce) and forge scenarios F01 to F18. E26 checks that no milestone of a later stage is proposed. Still unwritten: rating the DM's use of the fortune trend, and keeping "tragedy" within the content rating.

## Campaign plan and objectives

A live playthrough showed that players got no direction (milestones were free prose only the model could complete) and that maps had nothing to do with the story (the first map came from pitch keywords, every later one was improvised mid-play). The fix moves the model's work from play time to prep time: the story bible becomes an engine-ready **campaign plan**, the engine validates it, builds the maps from it and tracks progress itself.

**Built (phase A: contracts and the pure engine, `packages/schemas/src/campaign.ts`, `packages/engine/src/campaign*.ts`, `objective*.ts`, `spawn.ts`, `data/campaign.json`; contracts in `docs/contracts.md`, WS v9):**

- The bible's optional `locations`, `cast`, `encounters`, `key_items` and `ending`, plus an optional `hint` and `trigger` (`reach_location`, `defeat_encounter`, `obtain_item`, `talk_to`, `story`) on each milestone. `story` (the default) is today's behavior: the DM completes it.
- `validateCampaign` (reference integrity, a connected location graph, stages covered in order, a machine-checkable share of milestones and a machine-checkable final stage; thresholds in data) and `buildFallbackCampaign` / `ensureCampaignPlan`, a deterministic offline plan derived from the plot stages, the milestones and a seed (one location per stage, a quest giver, an ally, an encounter per later stage with a boss at the end, a key item, an ending, triggers). The built-in Lantern Marsh bible, the fake model and offline play get a valid plan this way.
- `locationMapBrief` turns a plan location into a brief the existing generator accepts (its own setting, one exit per connection, slots for the cast, enemies, boss and loose key items); `locationExits` and `resolveExit` say where each pending exit leads.
- `installLocationContent` runs once a location's map is added: it binds the location to the map, places the cast, registers the archetypes the server built and spawns the encounter, and places the key items (in an NPC's pockets, on the toughest creature of the holder encounter so it drops on defeat, or in the location's loot pile). The binding lives in the optional `GameState.campaign`.
- `trackObjectives` judges every machine-checkable milestone from state and the latest events with no model call, in stage order, and awards the milestone growth like `complete_milestone`. The DM's `complete_milestone` still works for `story` milestones and is rejected for machine-checkable ones (unless the engine can no longer meet the trigger).
- `objectiveView` (stage title and goal, the current stage's milestones as `{ id, hint, done }`, progress, finished) is in `state_snapshot` and the `objective_update` message. Players never see later stages or trigger internals.

**LLM layer (built).** Story bible generation (`packages/llm/prompts/story-bible.md`, `bible.ts`) asks the model for the whole plan: locations tied to plot stages and linked into one route, a named cast, escalating encounters, key items, an ending and milestones that each carry a player-facing `hint` and, wherever the engine can see it, a machine trigger. `checkBible` runs the plot check and then `validateCampaign`, so the single repair call is told exactly which plan rules failed. If the plan is still invalid, a reply with a sound story and plot keeps its story and gets the engine's offline plan (`ensureCampaignPlan`); any other failure falls back to the built-in Lantern Marsh bible, which carries a hand-written plan (so does the fake provider's bible). The bible call's output cap is 9,000 tokens.

**The DM leans on the plan (built).** When the bible has a plan, the per-turn context carries an `<objective>` block in place of `<milestones>`: the open milestones of the current stage, each marked `[engine completes]` or `[you judge]`, the ending goal, and, for the plan location the party is in, its summary, living cast, planned fights, loose key items and where its exits lead (never the whole plan). The server builds it with `objectiveContext(state)`. `dm-system.md` asks for narration of 25 to 70 words (up to 110 on `high_stakes` beats; 20 to 45 in combat), a next step toward an open objective in every non-combat reply (through the fiction, never read out), the plan's places, people and fights before invented ones, and `complete_milestone` only for `[you judge]` milestones. The narration clamp is 120 words. Evals B01 and B02 (valid plan on the first reply) and E31 to E34 (brevity, direction, engine milestones, plan use) are written; the evals were not run after these prompt changes, so `pnpm eval` must be run before a release.

**Server wiring (built).** At start the server makes the bible a plan (`ensureCampaignPlan`, validated; a bible with no plot or an invalid plan keeps the keyword start), builds the first location from `locationMapBrief` (map `m_start`), builds its encounter creatures through the enemy builder (the engine's own builder by default, `enemyBuilder: "engine"`; with `"model"` the model proposes and the engine builder is the fallback), designs the cast looks, installs the content, places the party and runs `trackObjectives` once. The opening DM note names the place and the first objective.

**Travel (built).** A PC standing on an exit of a campaign map outside combat takes the whole party to the plan location behind it (`resolveExit`). Locations next to the party's are prepared in the background (map plus model calls only, no live state, deterministic seed from the game seed and location), so the install is synchronous inside the session queue and a player waits only for a build still in flight. Creatures are refitted to the party's level and size at install and weakened (lower level, then weakest in-range stats) until the fight fits the standard encounter budget; a fight that cannot fit at level 1 stays over budget and `start_combat` raises its difficulty.

**Objectives in play (built).** `trackObjectives` runs after every DM action batch, scene change, combat step and end, pickup, gift, container action and `talk` act. Completion lines are shown as engine lines and passed to the DM on its next call. `objective_update` is broadcast whenever the view changes. Once the story is finished the DM is told once to bring the campaign to its ending; the session is not ended automatically.

**Web client (built).** The objective tracker lives in the side panel under the party bar. It collapses to one line, the choice is stored in `localStorage` under `aedm.objective.collapsed`, and it is hidden when the snapshot has no `objective`. `objective_update.completed` and stage changes add system lines to the story log. The mock (`?mock=1`) plays a three-stage plot, and `__mock.advanceObjective()` completes the next objective.

**Route view (built).** The campaign map the party actually knows: a `RouteView` (nodes, edges, markers, current), built by the pure `routeView(state)` (`packages/engine/src/route-view.ts`) from the plan and the campaign binding. Players see the places they have visited plus the places those name through their exits (known, unvisited); never later places, encounters, items or triggers. Visited nodes carry the plan summary. Neighbours of the current place carry the name of the exit that leads there. Open objectives the engine can place (`reach_location`, `defeat_encounter`, `obtain_item`, `talk_to`) are markers on shown nodes. Node ids are opaque hashes. The layout (connection depth columns, rows by plot stage then plan order, numbers in `data/campaign.json` `route`) is computed over the whole plan so nodes never move; a node's column therefore hints at its depth in the plan. It rides in `state_snapshot.route` and the `route_update` message, sent whenever the view changes (`syncRoute`, next to `syncObjective`); WS stays at 9 because this ships in the same unreleased version as the objective view. The web client shows it as a "Route" tab (SVG node map; select a place for its summary and how to get there; "Walk to the exit" reuses `move_intent` on the exit tile). Groundwork for an expedition-style presentation. Limits: the exit label is matched against map exit names, so a map without that exit shows the advice text but no button; a DM-generated map is "off route" (no node is current).

**Known limits.** Arrival always lands at the map's `party_start`, so going back through an exit does not put the party beside it. One PC stepping on an exit moves the whole party. A milestone whose `obtain_item` or `talk_to` holder could not be placed at install could stay open (a `defeat_encounter` with no creatures is released by `triggerBlocked`). Background preparation spends enemy-builder and sprite calls on neighbors the party may never visit. A DM `generate_map` is not tied to the plan.

**Choices worth knowing.** Triggers are judged from state, not only from events, so a missed event cannot lose progress: visited places and talked-to NPCs are remembered in the binding, items are read from inventories, and defeats from the entities. A visit or pickup made before its stage is current counts once the stage arrives. `adjust_plot` replaces the milestones of future stages with plain ones, so those become `story` milestones. Encounter creatures are spawned when the map is installed and are not budget-checked against the party at that moment (the server's enemy builder clamps them to the role); a DM `start_combat` still applies the usual budget check.

## Decisions and MVP scope

1. **Spikes are not a gate.** The spike kit's fixtures and evals are reused as tests and eval scenarios, but `apps/web` and `apps/server` are built alongside them. (Diverges from the original phase plan.)
2. **Renderer:** Canvas 2D for placeholder shapes. Revisit a game framework when real art lands.
3. **Persistence:** in-memory rooms. Save states stay JSON files (`<data>/saves/<room>/<save>.json`), and accounts are JSON files too (`<data>/accounts/`), behind an `AccountStore` interface so a database can replace them later. `AEDM_DATA_DIR` sets the data folder (default `data/`); `AEDM_SAVE_DIR` still overrides the save folder.
4. **Accounts (optional):** guests still play with an anonymous display name and the per-room reconnect token, so friends can join in seconds. An account (username, password, display name) unlocks saved characters, a "My campaigns" list with resume, and ownership of saves.
   - *Passwords:* scrypt (N=16384, r=8, p=1, 16-byte salt, 64-byte key), stored as `scrypt$N$r$p$saltB64$hashB64`, compared in constant time. Unknown user and wrong password give the same `auth_error` and take the same time (a dummy hash is checked). Usernames are 3 to 20 characters of `[a-z0-9_-]`, case-insensitive and unique.
   - *Sessions:* a random 32-byte token (base64url) is returned once by `register`/`login`; only its sha256 is stored (`sessions.json`) with a 30-day expiry that slides on use. At most 10 sessions per user (oldest dropped). The browser keeps the token in localStorage and sends `resume_session` on every connect. `logout` deletes it.
   - *Limits:* 5 register/login attempts per connection per minute, and 5 failed logins per username per minute (then `rate_limited`, even for the right password until the window passes).
   - *Connection-level auth:* the login belongs to the WebSocket connection, so account messages work before joining a room. A logged-in player's seat carries `user_id`; reconnecting to a room they sit in rebinds them even without the room token.
   - *Characters:* `Character.user_id` stays the in-room player id (the engine, views and `owner_player_id` all key on it). The account link lives on the server-side player record and in save metadata (`player_user_ids`).
   - *Saved characters:* a template is the creator's `CharacterCreate` plus an id and, once used, the forged abilities (display only). Claiming one (`claim_character` with `character_id: "template"`) re-runs the normal forge path.
   - *Saves:* save files carry `owner_user_id` (the host's account at save time; null for guest rooms), `campaign_title`, and `room.player_user_ids`. `list_campaigns` scans the save folders for saves the account owns (latest autosave per campaign plus named saves). `resume_campaign` opens a new lobby; the host loads the save with `load_save`, and logged-in players get their own characters back by account. An account-owned save can only be loaded by its owner. Guest-hosted saves belong to nobody and appear in no list.
   - *Not built yet:* email and password reset, OAuth, per-IP rate limits, changing the password or display name, deleting an account.
5. **Open settings:** maps are described by an open-ended setting, a layout generator and materials (see Content model). Forest, dungeon, desert, town and interior survive only as setting presets.
6. **Level cap 10**, party size 2 to 6 (1 allowed in dev mode).
7. **Map generation is procedural and deterministic** from the DM's map brief and a seed; the model never emits tiles.
8. **Server turn loop** (`apps/server`): one serialized async queue per room runs DM turns, AI combat turns and timeouts; player actions that are plain engine calls (a move, an attack on your own turn) apply immediately and synchronously. DM actions are applied one at a time in order. `create_enemy` carries an optional `ref` (`en_` + snake_case) that the server registers the built archetype under, so a later `spawn_entity` and `start_combat` in the same response can name it. The server snaps a blocked spawn tile to the nearest free one and swaps archetype ids in `start_combat` for the spawned entity ids.
9. **Beats and combat narration:** a beat closes when every online player with a character has spoken in character, or 6 seconds after the first message. A check is settled inside the beat from the DM's pre-written `on_success`/`on_failure` text (see decision 14); only a check without branch text, or in a `high_stakes` response, pauses the beat for one follow-up DM call. In combat the engine narrates an ordinary round from templates (decision 15). In `combatDm: "full"` mode the DM is called at the start, for reactions, at a round boundary when speech or a reaction trigger is still waiting, and when the fight ends; the default lean mode narrows that to dramatic beats (decision 19). The rest of this decision describes full mode. The DM is present between those moments:
   - *Speech:* in-character lines said during combat are free (no action cost). They are queued, go to the next DM call as `<player_input>` like beats, and wake the combat loop, so a line said mid-turn is answered before the speaker acts when the round's reaction is unspent.
   - *Reactions:* when an engine step produced `morale_broken`, `surrendered`, `fled`, `bloodied`, a downed character, a defeated allied NPC or a defeated boss or elite (`hasDramaticBeat`), or player speech is queued, the server runs one extra DM call the next time the combat loop runs (after an engine step, or at once for speech), before the next turn starts. The turn timer is cleared for the call and restarts in full, so a reaction never eats a player's turn. At most `combatReactionsPerRound` (server config, default 1) reactions run per round; further triggers stay queued and flow into the round narration. A reaction reuses `dmTurn` (a requested check still gets its one follow-up call) and is awaited on the room queue exactly like the round narration, so it cannot re-enter `advanceCombat` or skip a turn.
   - *Context:* a `<combat>` block (round, active creature, initiative order with side, HP, conditions and, for enemies, role, a concept cut to 100 characters, behavior, morale and bloodied) is added while a fight is on. Positions stay in `<scene>`.
   - *Combat-safe actions:* while `GameState.combat` is set the engine refuses every DM action except `rules.npc.combatSafeActions` (`npc_say`, `apply_condition`, `request_check`, `end_combat`, `set_fact`, `npc_note`, `open_thread`, `close_thread`, `suggest_actions`, `update_quest`), and allows at most `npc.maxCombatConditions` (1) `apply_condition` per response. `npc_say` may voice any living creature in the scene, enemies included. One predicate, `combatRefusal`, covers the engine and the server's `create_enemy` and `generate_map` pre-pass.
   - *Allies:* living `ally` NPCs on the map join `start_combat` automatically. `combatOutcome` is by side and unchanged: standing allies keep the party side up, so the fight is lost only when no party-side creature stands.
   A scene change (including an automatic move to a newly generated map) is a safe break and the engine's `rest` runs.
10. **Absence:** a player offline for more than 5 seconds is marked offline and their character is protected by the engine's `setAbsent`. If it becomes their combat turn and the turn timer runs out, the other players vote skip, wait or autopilot (majority decides).
11. **Level-up flow:** the owner chooses a score point, a new ability, a reforge or "keep my abilities" through `level_up_choice` (see contracts). Abilities are forged at the new level and must fit the power budget that is still free; a character may hold up to 6 abilities (`abilityLimits.maxAbilitiesPerCharacter`; creation still allows 1 to 3). Choices are refused during combat. The web client shows a "Level up!" badge and a modal, plus a read-only character sheet from the party card.
12. **Hosting on Cloudflare (`apps/edge`):** one Worker serves the Vite build as static assets and upgrades `/ws` into a single `GameHub` Durable Object (SQLite-backed, so the free plan works). The hub runs the same `createGameCore` as the Node server, so every room, timer and invite code lives in one object; sharding by room is the next step if one object is ever too small. Storage sits behind `KvBackend` (`apps/server/src/kv.ts`): `FsKv` for Node, `DoKv` (chunked values) for the Durable Object. Saves, accounts, the Workshop and assets all use it, so the two hosts differ only in the backend. WebSockets are accepted without hibernation because rooms hold live timers and in-memory state; autosaves are what survive the object being evicted. Prompt files are bundled as text and registered with `registerPrompts`. Open risk: scrypt (about 50 ms of CPU) may exceed the free plan's CPU limit per request; it worked under `wrangler dev`, so test it on a deployed Worker before relying on the free plan.
13. **Model providers:** `fake` (default), `anthropic` and `gemini` sit behind `ModelProvider`; `createProviderFromEnv` picks one from `AEDM_LLM_PROVIDER` for both the Node server and the Worker. The Gemini provider uses plain `fetch` with SSE streaming (no SDK), the key in a header only, and per-tier model names that can be overridden because Google retires preview names. Gemini 3 models run with a low thinking level by default (`AEDM_GEMINI_THINKING`), because thinking tokens count against the output limit. Free Gemini limits are small and change; rate limits surface as retryable `rate_limit` errors. Free-model output validates less often, so more turns go through the one repair call.
14. **Checks resolve in the same beat:** `request_check` carries optional `on_success` and `on_failure` (1 to 60 words). The engine rolls, the server broadcasts the matching text as a separate `narration_chunk` (new turn id, no new WebSocket message, `WS_VERSION` unchanged), records it in recent turns, and queues the engine lines in `pendingLines` so the next DM turn sees the result. The text is sanitized like narration and is flavor only. The follow-up call remains as a fallback for models that omit the text and for `high_stakes` responses (the pivotal case, so no new field). Adding optional fields keeps the DM response `v` at 1, as with earlier additive changes. Expected saving: one full DM call per beat with a check (roughly half the tokens of such a beat). The prompt change needs `pnpm eval`.
15. **Deterministic narrator and intent router:** the model is called only where it adds something the engine does not know. Combat rounds are narrated by `narrateEvents` (templates in data, seeded rng). In `combatDm: "full"` mode a real DM call happens at combat start, when a boss or elite goes down or a PC drops to 0 HP (`isDramaticEvent`), and at combat end; lean mode (decision 19) replaces the start and the end of an ordinary fight with engine text. Outside combat, `classifyIntent` recognizes only full-sentence mechanical commands against the current scene; it is conservative on purpose, and anything it is unsure about is narrative. Object commands (open, take, examine and so on) were first left to the DM; decision 18 moved them into the router, and decision 22 widened it again. Talk stays narrative. A walk whose path fails is handed to the DM. A compass step moves one tile. `ServerConfig.intentRouter` (default on) switches the router and the empty-input guard off for comparison.
16. **Token diet for the DM call:** the per-turn context is bounded and prioritised instead of dumping all state (see AI layer), the DM repair call omits the context, and each purpose has an output cap. Reason: input tokens grow with the campaign and the system prompt is paid on every call; the DM keeps what it needs to stay consistent (nearby facts, open goals, the latest narration in full). Prompts changed, so run `pnpm eval` before a release.

17. **Mechanical interactions belong to the engine (containers, locks, doors, levers, signs, loot):** the common, repeatable parts of play (opening a chest, taking an item, unlocking or forcing a door, pulling a lever, reading a sign, looting remains) are resolved by pure engine functions and need no DM call; the DM is for what only a narrator can do (a creature, a surprising use). Altars moved to the engine in decision 26. Each choice and why:

18. **Interactions are wired end to end (server, router, DM):** `act`, `container_action` and `inventory_action` call the engine in `GameSession` and never the model (creatures and `talk` still become DM intents; altars no longer do, see decision 26). Outside combat the verb applies at once; in combat it goes through `combatAction`, so only the active character acts and `combatCost` is charged by the engine. `publish` sends `log` lines (an examine line is a `narration` log) and the diff path carries `containerDiff` (`containers_changed`, `containers_removed`, `interactables_changed`), so every client stays current; the opener alone receives `container_view`. `classifyIntent` gained the typed object commands, conservatively (see Game loop, Intent routing). Three DM actions let the story shape the world without breaking the engine's ownership of items: `stock_container` (items into a chest, pile, remains or, by NPC id, pockets; same loot-cap and tier checks as `grant_item`, all or nothing, at most `pileCap` items per container), `set_sign_text` and `set_lock` (a door or chest, DC 5 to 30, optional key name; keys reach players only through `grant_item` or `stock_container`). All three are outside `combatSafeActions`, so they are refused in combat. The DM sees containers and objects in `<scene>` (ids, position, lock DC, item names only for opened chests, capped); players, not the DM, open things. Generated door objects are now on (`interact.doors.generated.enabled`): doors are what levers link to and they make rooms matter; locks never dead-end (pick or force always works), the router and `act` can open them, and web clients must render door state from `interactables_changed`. Cost: about 195 tokens added to the DM system prompt, and a typical context grows by about 90 tokens when a scene has a handful of containers. The prompt changed, so run `pnpm eval` before a release.
    - *Where state lives:* `GameState.containers` (chests, piles, remains, pockets) and `GameState.interactables` (door, lever and sign changes). Maps are shared by reference and never mutated, so changes are an overlay that snapshots merge in. A chest is both a map object and a container (linked by `object_id`); its state is derived from the container so the two cannot disagree.
    - *Determinism and the loot cap:* chest and loot-slot contents are rolled from a stream seeded by the map's seed and the object id, with the party level at that moment, inside a budget below the encounter loot cap. Chest stock is scenery and does not count against `session.lootValueThisEncounter`; remains drops do, exactly like `grant_item`, and use a forked stream so they never shift combat rolls.
    - *Combat rule (the simple one):* every verb is allowed in combat at a cost from data (taking, opening, doors, levers and locks use the action; dropping and giving the quick action; reading and examining are free), and a verb can be set to `refuse`. No new turn machinery.
    - *Locks never dead-end:* a lock can always be picked or forced, a failed pick costs only the attempt, and forcing is noisy. Validation therefore treats doors as passable and the map rules are unchanged.
    - *Bound gear:* weapons and armor equip on pickup and cannot be dropped or given, which stops a tier being copied between characters. The engine pack cap (24) is lower than the schema's 100; `grant_item` keeps its own.
    - *Rollout:* generated door objects were off at first; decision 18 turns them on (`interact.doors.generated.enabled`).
    - *Contracts:* Map stays v2 (optional `lock`, `links`, `text`), Container is v1, `WS_VERSION` is 7. Object verbs extend `act`; item moves are `container_action` and `inventory_action`.

19. **Lean combat (default, `ServerConfig.combatDm: "lean"`):** the engine narrates what it can and the DM is called only where a narrator adds something. The engine writes the opening of a fight it started (`narrateCombatStart`: the foes grouped with counts, who moves first), a short bark when a creature's nerve breaks, it yields or flees, or (half the time) a boss or elite is bloodied (`barkFor`: spoken words for body plans that talk, a described reaction for the rest; a spoken bark goes through `npc_say` so a surrendered creature remembers it), and the close of an ordinary victory (`narrateCombatEnd`). The DM is still called for: a party member dropping to 0 HP, a boss or elite defeated, player speech during the fight, a defeat, and a victory that involved a boss or elite or left a party member down (`victoryNeedsDm`). Everything the engine narrated is added as `[engine: ...]` lines to the DM's next call and the text goes into the recent turns, so the DM stays consistent. `"full"` mode keeps the earlier behavior (decisions 9 and 15) for comparison. Phrasings, bark chances and the victory rules live in `data/combat-voice.json`.
20. **Engine-started fights and the calm flag:** outside combat the engine starts a fight in three ways, all through one server path (`startEngineFight`, lean mode only): the attack button (`basic_attack` on a hostile enemy), a typed "attack <unique enemy name>" (the router verdict `attack`), and aggro. `planEngagement` and `planAggroEngagement` pick the participants (every standing party character on the map, living allied NPCs, the hostile creatures that noticed or were attacked and, unless `joinAll`, those near them) and the lowest difficulty from standard up whose budget covers the foes' threat. In full mode, or when the engine cannot start the fight, the attack stays an intent for the DM. If a fight begins while a beat is routed, the beat's remaining intents are handled like intents during combat. Aggro (`aggroCheck`, `ServerConfig.aggro`, default on, lean only) is checked after a party character moves outside combat (a click-walk step, a compass step, a routed step) and when the party arrives in a scene, never when a creature is spawned: a hostile creature within `rules.ai.aggro.radius` tiles with line of sight (walls, smoke and closed doors block it) notices the party. The opening then says the creatures noticed the party instead of crediting a character (`start_noticed` templates), and a pending `[engine: ...]` line tells the DM. `Entity.calm` stops a repeat: when a combat ends, every surviving enemy-side creature (after a truce, flight or party defeat) is marked calm and `aggroCheck` ignores it as a noticer and as a joiner; starting a combat with it (the DM's `start_combat`, or a player attacking it) clears the flag. The field is optional, so old saves load, and it is saved with the entity.
21. **Offline enemy builder (`enemyBuilder`):** `buildEnemyOffline` (`enemy-builder.ts`, data in `enemy-kits.json`) turns a concept, a role, the setting notes, the party level and an optional `ref` into a valid enemy with no model call: a name from the ref or the concept, an element theme from keywords (resistance, weakness, loot hint, sprite tags), trait shifts from keywords (armored, swift, brute, frail, deadly), behavior lines that the tactics patterns read, and abilities from the theme's kit scaled by role. The result passes the same `clampEnemy` and `validateEnemy` checks as a model enemy. `ServerConfig.enemyBuilder` is `"engine"` by default (no model call for stats; the server still designs the sprite and registers the archetype as before; the seed comes from the game seed and the archetype count, never a clock) or `"model"` (the old path, which now falls back to the offline builder when the model call fails, instead of making no enemy). Reason: one model call fewer per new enemy type, and a failed call used to leave the DM's `spawn_entity` with nothing to spawn.
22. **Wider router and engine descriptions:** `classifyIntent` also recognizes looking around, checking the pack, waiting, using the healing draught by name, examining a uniquely named creature, attacking a uniquely named enemy (decision 20) and more walking phrasings. The engine answers with `describeScene`, `describeCreature` and `describeInventory` (`describe.ts`, `data/describe.json`): the place and mood, exits with the map edge, the objects, open containers by label, and the creatures nearby with a health word, never numbers. They never reveal an NPC's concept, notes, voice or lines, an enemy's concept or behavior, the contents of a closed or locked container, or hit points as numbers. A look is shown to the table and the DM hears only that it happened. Trade-off: examining a creature is now a deterministic line (name, appearance, a health word, conditions) instead of DM prose, so it can no longer drop a story hint.
23. **AI upgrades (engine):** enemies and allied NPCs aim area abilities at the tile with the best net count of foes over allies (`rules.ai.areaAllyPenalty`), use support abilities (heal, shield, check bonus) on allies, kite (a ranged creature with a foe adjacent steps to a tile that is adjacent to no foe but keeps range and sight; `rules.ai.kite`), take a finishing blow (`rules.ai.finish`: a foe the creature can plausibly drop this turn is ranked first) and avoid hazards (`rules.ai.hazard`: fire and visible traps of the other side are skipped when a detour of at most `detourAllowance` extra tiles exists; a step that would otherwise make no progress crosses the hazard, so a band wider than the creature's speed is crossed rather than stalled at). Enemies with area and support abilities are stronger than before, and balance was not re-simulated.
24. **Allies keep up:** out of combat, after a party character moves, each living allied NPC more than `rules.ai.follow.maxDistance` tiles from the nearest standing character walks up to `stepTiles` toward them and stops within `stopDistance` (`followStep`); the server runs it before the aggro check. At a scene change the `change_scene` action (and the server's move to a freshly generated map, `placePartyWithAllies`) takes along the allies within follow distance of the party, picked before the party moves and placed after it so they take the free tiles around the characters.
25. **Known limits of this round of changes:** (a) the DM prompt was not changed, so the DM is not told that hostile creatures attack on sight; it learns of an engine-started fight from the `[engine: ...]` lines and may still plan an ambush that the engine pre-empts. (b) No eval was run (`pnpm eval` costs money and was not asked for); the effects of lean combat, the shorter fight context and the offline enemies are unchecked against a real model. (c) The new `rules.ai` numbers (`areaAllyPenalty`, `kite`, `finish`, `hazard`, `aggro`, `follow`) and the numbers in the new data files are untuned first guesses. (d) Examining a creature is a fixed line (decision 22). (e) Enemies with area and support abilities are stronger, and enemies the engine builds have new kits; balance was not re-simulated.

26. **Map traps, searching and altars (WebSocket v8):** (a) *Traps* are an interactable kind `trap` (`closed` armed, `open` harmless), often `hidden`, placed by the generator (`interact.json` `traps`). `enterTile` springs one on a player character or allied NPC (a save for half, `trap_sprung`); enemies never do. `spotCheck` reveals hidden traps passively (10 plus Wisdom perception against the trap DC, radius `traps.spotRadius`, line of sight, no dice) and the server calls it after every party move, after a scene change and at game start; a walk in progress stops when something is spotted. `disarm` is a rolled DEX check on a revealed armed trap. (b) *Searching* is `act` `search` (no target) or a typed "search the room": one WIS roll that tries every hidden trap or chest within `search.radius`, each character once per object. The table gets `searchedText` only, a miss and "nothing left to roll against" read the same, no `roll_result` is sent and the total is never shown; the DM line may state what was found. (c) *Altars*: `interact` (or typed "pray at the altar") gives a once-per-character boon (mend, ward or cleanse) through `performAct`, with no DM call; a repeat is `altar_silent`. (d) *Hidden objects do not exist for the table.* `findInteractable`, `effectiveMap`, `containerSummaries`, `containerDiff`, `describeScene`, `isContainerHidden` and the server's `visibleObjects` filter them out of snapshots, the map payload, diffs, the router context, walk targets, click targets and container views; only the engine (`findInteractableAny`) and the DM context (which marks them `hidden`, and shows a trap as armed or harmless) see them. The DM may stock or lock a hidden chest; that reveals nothing (tests in `apps/server/test/hidden-leak.test.ts`). A reveal (spotted, searched, sprung) reaches clients as `state_diff.interactables_revealed` (the public map object, never the trap or altar detail). Player-facing phrasing for these events lives in `interact.json` `texts` (`trap_event`, `search`, `altar_use`); engine events carry numbers and coordinates that only the DM may hear. (e) *Walking:* click-to-move and walk-to-target avoid revealed armed traps whenever any other path exists and refuse the walk (with a message from data) when the only path crosses one, unless the clicked tile is the trap itself; arrow keys and `move_dir` are deliberate single steps and are never blocked; a trap sprung on a walk ends it, and a trap found mid-walk stops it. Allies and enemies route around known traps through `hazardTiles`. (f) *Downed outside combat:* the engine had no recovery path (a downed hero cannot act, nothing ticks out of combat, a scene change is the only rest, and the DM prompt does not know to call one), so a trap could soft-lock a solo player. Fix without new numbers: when no player character is left standing outside combat, `wakeIfWiped` wakes everyone at `downed.wakeHp`, as the end of a fight does. With a friend still standing, a downed hero stays down until healed, revived or a scene change, as before. (g) *Known limits:* the numbers in `interact.json` (`traps`, `search`, `altars`) are untuned first guesses; the DM prompt was not changed, so the DM is not told about traps, searching or altar boons (it sees them only as `[engine: ...]` lines and `<scene>` entries), and no eval was run; `chest.hiddenPct` is 0, so hidden caches are opt-in (a map must set `hidden` on a chest); passive spotting runs only out of combat; an ally can still cross a known trap when the detour is longer than `rules.ai.hazard.detourAllowance`; a trap that downs a hero in combat follows the ordinary downed rules.

## Roadmap

- **M0 (this slice):** schemas, engine core (rules, cost, threat, mapgen), LLM layer with fake provider, server with lobbies and the exploration loop, web client with lobby, map, chat and shapes.
- **Content model (done):** schemas, contracts and prompts for `SpriteSpec`, materials, palette, map brief v2 (`setting`), map v2 (inline tileset) and asset records.
  - Map generator: `packages/engine/data/materials.json` (about 170 materials with aliases), `data/settings.json` (20 setting presets, keyword accents, layout fallbacks), eight layout generators in `packages/engine/src/map/layouts/`, inline tilesets, and a seed-then-fallback chain.
  - Sprite designer: `finalizeSpriteSpec` and `designSpriteOffline` (engine), `designSprite` (llm), and the server asset store in `apps/server/src/assets/` (cached per concept, 4 s timeout to the offline designer).
  - Web renderer: all 19 patterns with role treatments and mood, the sprite composer (10 body plans, 45 parts, poses), the creator sprite builder, and a QA gallery at `?mock=1&gallery=1`.
- **M0 level-up (done):** engine `levelUpView`, `spendScorePoint`, `addAbilityToCharacter`, `replaceAbility`, `skipAbilityPick`, `addGrowth`; server `level_up_choice`; web modal, character sheet and mock scenario. Known gaps: no undo or respec; the power budget is not re-validated when an ability's level caps change; abilities can only be reforged one at a time (one pick each); `/dev grow` is the only way to level without the DM awarding growth; enemies do not scale to the extra abilities.
- **M1:** full combat loop in the client, ability forge UI, enemy builder, saves and reload.
- **M2:** memory (summaries, retrieval), evals in CI, content safety pass, mobile polish.
- **M3:** image generation pipeline and acceptance gates from the style bible.
- **Next (designed, not built):** generated art for player-made sprites (M3). Player-made sprites (Describe, Paint over, Paint from scratch, Workshop, campaign cast) and story structure are built. See the sections above.
